# Database design

All identifiers are UUIDs and all timestamps are UTC `TIMESTAMPTZ`. Monetary values are PostgreSQL `BIGINT` paise. `ledger_entries.amount_paise` is signed: positive debit, negative credit; a posted transaction sums to zero. Customer accounts are normal user balances; system clearing accounts model external deposits and withdrawals.

`users`, `roles`, and `user_roles` establish identity. `accounts` has customer/system kind and status. `account_permissions` supports account-level access. `ledger_transactions` is the business posting envelope; `ledger_entries` are immutable movements. `idempotency_keys` uniquely binds a user request key to a request fingerprint/response. `transaction_attempts` preserves refused/error attempts without pretending they posted and migration `007_attempt_account_scope.sql` associates current/new attempts with their source account. `audit_events` records actor, entity, and metadata. `account_limits` stores bounded daily controls.

Indexes cover owner lookup, transaction status, account statements, transaction lookup, attempts, and audit entity lookup. `ON DELETE RESTRICT` protects financial history. The migration runner records applied filenames in `schema_migrations`, runs each migration in a transaction, and never silently re-runs it.

Migration `008_reconciliation_history.sql` adds `reconciliation_runs`, `reconciliation_findings`, and one disabled-by-default `reconciliation_schedules` row. Runs and findings are evidence/history; marking a finding resolved stores an investigation note and approver identity but does not mutate account snapshots or ledger entries. The API applies a repeatable-read snapshot for manual reconciliation. A separate worker claims a due schedule row using row locking and persists its run/findings and next-run time atomically. Analytics is computed from `ledger_transactions`, `ledger_entries`, `accounts`, and `transaction_attempts`; no analytics/demo fixtures are generated.

Migration `009_scheduled_payments.sql` adds schedule definitions, unique per-schedule occurrence timestamps, and per-attempt idempotency keys. A worker claims due occurrences with a two-minute lease and persists its idempotency key before invoking the existing `executeOperation` path. If it crashes after posting, lease recovery reuses that attempt key and receives the original stored response. A later insufficient-funds retry uses a distinct attempt number/key. Foreign keys preserve transaction history; scheduled-payment paths never update or delete ledger entries.

Migration `010_backfill_refused_attempt_accounts.sql` repairs rows left unassociated by migration 007. It matches refused attempts to their same-transaction `TRANSACTION_REFUSED` audit event using actor, timestamp, operation, reason, and amount; it does not guess when no exact audit match exists. Linked accepted attempts use the transaction source/customer ledger account where available.

Migration `011_auth_names_and_schedule_references.sql` adds the optional full name field and description/idempotent creation metadata for existing one-time payment instructions. Migration `012_separate_recurring_payments.sql` creates a dedicated recurring configuration and occurrence/attempt history model, copies legacy repeating rows and their histories, then limits the one-time schedule table to `once` cadence. The migration is additive for the new model and retains execution/transaction foreign keys; it removes only duplicated legacy repeating schedule/occurrence/attempt rows after their copies are inserted. Review backup/restore procedures before applying to production.
